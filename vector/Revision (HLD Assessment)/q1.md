### Part 1: Database Schema Design

1. Schema Defination
   1. **Users Table** : User (Unique ID(PK), email, name and related metadata)

      CREATE TABLE Users(
      user_id SERIAL PRIMARY KEY,
      email VARCHAR(255) UNIQUE NOT NULL,
      name VARCHAR(255) NOT NULL,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP

      )
   2. Calenders Table : Calender (Uid (PK), calender_name, )

      CREATE TABLE Calenders (
      calender_id SERIAL PRIMARY KEY,
      user_id INT REFERENCES Users(user_id),
      calender_name VARCHAR(255) NOT NULL,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP

      )
   3. Events Table : Calender (Uid (PK), calender_name, )

      CREATE TABLE Events (
      event_id SERIAL PRIMARY KEY,
      calender_id INT REFERENCES Calenders(calender_id),
      title VARCHAR(255) NOT NULL,
      description TEXT,
      start_time TIMESTAMP NOT NULL.
      location VARCHAR(255)
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
      updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATED CURRENT_TIMESTAMP

      )
2. Partition Strategy
   1. Horizontal and Vertical Partitioning
      1. Horizontal Partitioning (Sharding)
         * DIviding Users across multiple databases instances. Each shard would store subset of users and their associated calenders and events
         * Rationale: This reduce the load on individual databases instances and ensures that high-trafic queries are distributed across multple servers
         * sharding key : a user-specific attributes such as user_id or email_hash would be used to route requestst to approprite shards
      2. Vertical Partitioning
         * In case where schema become large, vertical partioning could used by splitting the table based on functionality
         * Rationale : this allows optimise queries and efficient data retreval for different use cases
